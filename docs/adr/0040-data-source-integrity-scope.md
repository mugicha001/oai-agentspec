# 0040: データ源インテグリティのスコープと責務境界

- Status: accepted
- Date: 2026-09-03

## Context

エージェントが判断材料として読む取得系データ源（RAG 検索結果・会話メモリ・静的資産を返すツールの
返却値）が取得時点から改変されていないことをどう扱うかは、既存の改竄防止機構 `lockdown`
（コア層 `integrity.py`）でも内容ガードレール層（`oai-agentspec[guardrails]`）でも明示されていない。
`lockdown` はディスク上の静的資産と宣言グラフを対象とし、取得結果には届かない。一方 guardrails 層には
ツール出力を検査する境界（`Boundary.TOOL_OUTPUT`）と接着ファクトリ（`tool_guardrail` / `guard_tool`）・
述語ラッパ（`predicate_detector`）・登録簿（`GuardrailRegistry`）がすべて実装済みで、欠けているのは
「どの境界へ何を装着すれば改竄検知になるか」「どこからが利用者責務・レイヤ外か」という知識である。
この境界が 1 箇所に定まらない限り、同種の要望が判断のやり直しを繰り返し要求する。

検討し却下した案は次のとおり。

| 却下案 | 却下理由 |
|---|---|
| 1. lib へベースライン管理機構を持ち込む案 | 保管先・保護手段（読み取り専用配置 / 署名 / HMAC）・鍵管理の選択が利用者環境に依存し、lib が決め打ちできない。ハッシュ再計算やベースライン照会の再試行を抱えると build-don't-run の逸脱を新たに増やす |
| 2. `lockdown` の `checks` へ寄せる案 | `IntegrityCheck` は `Callable[[], None]` で引数を取らず、検査対象のツール出力テキストを受け取れない。発火も `lockdown()` の呼び出し時のみで、1 ターンごとのツール出力に届かない |
| 3. guardrails をコア層へ統合する案 | guardrails は opt-in extra、`lockdown` はコア層（標準 lib のみ依存）。統合はコアから実行寄り層への依存辺を作り、単方向依存とコア `__all__` を宣言層シンボルのみに保つ既存の分離契約に反する |
| 4. ライブレスポンス向けに毎回検証を行う機構を作る案 | 呼び出しごとに値が変わるのが正常な応答には比較すべきベースラインが原理的に存在せず、検知として表現できない（見せかけの防御を導入しない既存方針） |
| 5. ツール境界の guardrail を型付きフィールド化する案（`ToolSpec` / `AgentSpec` へ専用フィールドを足す、または `Boundary` 由来の名前参照をツール境界へ届かせる案） | 新規コードの追加を伴い本決定のスコープ外。現状でも `ToolSpec.extra` の素通しキーとして宣言はできるため機能欠落ではなく、型付き検証が効かないという非対称が残るのみ。解消は別途の設計判断へ委ねる |
| 6. `runtime/governance` の tool ポリシーへ寄せる案 | 実行可否の許可 / 拒否であり、返却データの同一性検査ではない。責務が異なる |

## Decision

### (a) 新規コードを追加せず既存 guardrails 層と利用者 DI で満たす

データ源インテグリティは `src/` へのコード追加なしで成立させ、成果物は本 ADR・`docs/integrity.md` への
パターン記載・`examples/guardrails/` への example に限る。必要な部品（境界 enum・接着ファクトリ・
述語ラッパ・登録簿）はすべて実装済みであり、欠けているのは知識のギャップである。knowledge のギャップに
対してコードを足すと、公開シンボルが増えるうえに、ベースラインの保存形式・鍵管理という利用者環境依存の
選択を lib が決め打ちすることになる。検知の実行主体は SDK ネイティブの tool guardrail フックであり、
lib は接着のみを提供するため、build-don't-run 逸脱の一覧へ新たな項目を追加しない。重い専門検知
（PII / モデレーション / 注入検知サービス）を非同梱として利用者 DI とする guardrails 層の既存方針を、
ベースライン照合ロジックにもそのまま適用する。

### (b) 取得時点のベースラインの生成・保管・保護は利用者責務とする

比較対象となるベースライン（取得時点のダイジェスト等）の生成・保管・保護・失効・鍵管理は利用者責務と
し、lib はベースラインの保存機構も署名機構も提供しない。保管先（ファイル / KV / HSM）・保護手段
（読み取り専用配置 / 署名 / HMAC）・失効運用はいずれも利用者環境に依存し、lib が選択を固定すると
環境ごとに不適合を生む。lib が抱えれば、ハッシュ再計算ループやベースライン照会の再試行という
build-don't-run の逸脱を新たに増やすことにもなる。docs が提示するパターンでは、ベースラインの照会先は
利用者が渡すインメモリのマッピングまたは利用者実装の同期関数とし、追加の外部サービス接続を前提としない。

### (c) 検知の適用境界は `Boundary.TOOL_OUTPUT` を基本とする

RAG 検索・メモリ取得を `function_tool` として宣言し、その出力を `Boundary.TOOL_OUTPUT` で検査することを
基本の適用境界とする。取得をツールとして宣言すれば、検査点は「ツールが返した直後・モデルが読む前」に
一意に定まる。agent 境界（INPUT / OUTPUT）は会話の入出力を対象とするため、取得結果がモデルへ渡る瞬間を
捉えられない。改竄検知用途の既定挙動は中断（`on_trip="raise"`）とし、続行系（`"reject"` / `"allow"`）を
既定として提示しない。帰結として、ツール境界には型付きの宣言面が無いという非対称（宣言面のギャップ）が
残るが、本決定ではこれをコストとして記録し解消しない。取得をツールとして宣言しない構成では本経路が
成立しないため、そのような構成は適用対象外とする。

### (d) ライブなツールレスポンスの改竄検知はスコープ外とする

呼び出しごとに値が変わることが正常な API / DB 応答（ライブレスポンス）の改竄検知はスコープ外とする。
比較すべきベースラインが原理的に存在しないため、lib のレイヤでは検知として表現できない。この領域に残る
防御は次のとおり。トランスポート層の完全性（TLS 等）は lib のレイヤ外であり、利用者およびインフラの
責務として扱う。内容ガードレール（実装済みの `Boundary.TOOL_OUTPUT` 検査）は lib のレイヤで表現できるが、
取得時点との同一性を見るものではなく内容の妥当性検査であり、改竄検知の代替にはならない。静的資産
（ドキュメント本文・スナップショット・確定済みメモリ）を返す取得系ツールは (c) のパターンで検知できる
ため、境界はデータの性質（静的資産かライブレスポンスか）に引く。

### Issue の受け入れ基準への着地

本表を Issue 受け入れ基準の着地の唯一の記載箇所とし、他の節・他ファイルへ複製しない。

| Issue の受け入れ基準 | 着地 | 根拠 |
|---|---|---|
| RAG 検索結果・会話メモリの取得時点での想定外改変を検知できる方針 | 満たす | 取得をツールとして宣言し `Boundary.TOOL_OUTPUT` へベースライン照合 detector を装着するパターンを FR-2 で docs に記載する |
| ツール（API/DB）レスポンスの改変・偽装を検知できる方針 | 一部スコープ外として明記する | 静的資産を返す取得系ツールは上段と同一パターンで検知できる。毎回値が変わるライブレスポンスは比較対象のベースラインが原理的に存在しないため FR-4 でスコープ外と明記する |
| 検知時の既定挙動（fail-closed で拒否する等）の明文化 | 満たす | FR-3 で `on_trip="raise"` を改竄検知の既定として docs に明文化する |
| 既存 lockdown との関係（統合 / 併存 / 独立）の設計判断 | 満たす | FR-5 で「併存」と結論し根拠を記述する |
| 導入コスト（鍵管理・trust level 分割等）とトレードオフ | 満たす | FR-6 で ADR の `## Consequences` に整理する |

FR 番号は `docs/requirements/data-source-integrity.md` の要件番号を指す。

### `lockdown` との関係は「併存」とする

データ源インテグリティと `lockdown` の関係は「併存」（統合でも独立でもない）とする。根拠は次のとおり。

- (a) `lockdown` は起動時 / 明示発火時にディスク上の静的資産を検証する build-time 寄りの機構であるのに
  対し、データ源インテグリティは 1 ターンごとのツール出力に対する検査であり、発火タイミングが異なる。
- (b) `lockdown` はコア層（`src/oai_agentspec/integrity.py`・標準 lib のみ依存）にあり、guardrails は
  opt-in extra の実行寄り層にあるため、統合するとコアから実行寄り層への依存辺ができ、
  単方向依存とコア `__all__` の分離契約に反する。
- (c) 本決定は新規コードを追加しないため、統合の実装面が存在しない。

現在仕様の SoT は `docs/integrity.md` の「データ源インテグリティ（RAG / メモリ / ツール出力）」節と
し、本 ADR は判断・却下案のみを記録して仕様詳細を重複させない。

## Consequences

- + 公開 API・`__all__` のメンバ集合・既存利用者の挙動がすべて不変のまま、データ源の改竄検知パターンが
  利用可能になる。既存構成へ後から装着でき、既存テストスイートも無修正で緑を維持する。
- + 検知の実行主体は SDK ネイティブの tool guardrail フックであり、lib は接着のみを提供するため
  build-don't-run 逸脱の一覧に新たな項目が増えない。SDK 隔離も `src/` 無変更から従属して維持される。
- + 検知ロジックが利用者 DI であるため、ベースラインの保存形式・署名方式・失効運用を lib が縛らない。
  利用者は自環境の鍵管理・保管基盤に合わせて実装を差し替えられる。
- + `lockdown` と併存させたまま同一アプリで両方を使える。守る対象（ディスク上の静的資産と宣言グラフ /
  1 ターンごとのツール出力）が重ならないため、片方の導入がもう片方を置き換えない。
- - ベースラインの生成と保管が利用者の設計課題として残る。取得時点の正解をどう作りどこへ置くかは
  取得元システムの運用に依存するため、lib は保存機構を持たず肩代わりしない。
- - ベースライン自体の保護（読み取り専用配置・署名 / HMAC を用いる場合の鍵管理）が利用者の負担となる。
  鍵の生成・配布・ローテーションは利用者の運用基盤に属し、lib が抱えると環境依存の選択を固定するため
  肩代わりしない。
- - 情報源ごとの trust level 分割（信頼できる取得元と untrusted 取得元の宣言分け）を利用者が設計する
  必要がある。どの取得元を信頼するかは業務上の判断であり、lib が既定を与えられないため肩代わりしない。
- - ベースラインの失効と更新（元データが正当に更新された場合の運用。検索インデックスの更新が同一クエリの
  ヒット集合を変える場合を含む）が運用課題として残る。正当な更新と改竄を区別する権威は取得元システム側に
  あり、lib からは観測できないため肩代わりしない。
- - 宣言面のギャップが残る: 適用境界をツール境界に限る帰結として、`AgentSpec` の専用フィールド
  （`input_guardrails` / `output_guardrails`）も名前参照（`guardrails`）もツール境界へ届かない。利用者は
  `function_tool` の引数へ guardrail を手で渡すか、`ToolRegistry` 経由で宣言する場合は
  `ToolSpec.extra` の素通しキー（`tool_output_guardrails`）として渡すことになる。後者は
  型付きフィールドではないため、キー名の妥当性は build 時の `extra` 検証で確かめられる
  （未知キーは `ValueError`）ものの、宣言時には検証されず、値の型・形は検証されない。
  ツール境界の guardrail に型付きの宣言面が無いというこの非対称は、宣言でエージェントを構成する
  という本ライブラリの価値提案に対する欠けであり、本要件では新規コードを追加しない方針の下で
  解消しない。
- - トレードオフとして「lib へベースライン管理機構を持ち込む案」（Context の却下案 1）を採らない。
  鍵管理と保存先の選択が利用者環境依存であること、およびハッシュ再計算ループ・ベースライン照会の再試行が
  build-don't-run の逸脱を新たに増やすことが却下理由であり、その代償として上記の利用者負担が残る。
- - 攻撃者がベースラインと対象データの双方を同時に書き換えられる環境では検知保証が失効する。これは
  `docs/integrity.md` の manifest 信頼境界の節と同じ前提であり、本決定でも解消しない。

## Confirmation

本決定の強制手段は「docs 記載 + example の実在」であり、**自動テストによる強制手段を持たない**。
`src/` の振る舞いを変えない決定であるため、強制手段となるテストを書く対象が存在しない。

「守られている」ことの確認手順:

1. `docs/integrity.md` に「データ源インテグリティ（RAG / メモリ / ツール出力）」節が存在し、
   `Boundary.TOOL_OUTPUT` を適用境界とする経路と、改竄検知用途の既定が `on_trip="raise"` である旨が
   記述されていること。
2. `examples/guardrails/09_data_integrity_detector.py` が実在し、実 API での手動実行で正常系
   （ベースライン一致）と改竄系（ベースライン不一致で中断）の 2 経路が期待どおり終端すること。
3. 本決定が `src/` 無変更で成立していること。これは決定時点の確認であり、継続的に強制される性質の
   ものではない。

`docs/QUALITY-GUARANTEES.md` へは行を追加しない。機械検証できる不変条件を新設しない（`src/` の
振る舞いを変えないため、台帳が指すべき強制手段テストが存在しない）ためである。

本決定を覆す場合は、ADR の append-only 規約に従い新規 ADR を起こし、本 ADR の Status を
`superseded by NNNN` に変更する（本文そのものは書き換えない）。
