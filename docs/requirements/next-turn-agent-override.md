# ハンドオフ後の次ターン開始エージェントの宣言的上書き（Next-Turn Agent Override・初版）

## 命名注記

本書のシンボル名（`NextTurnPolicy` / `resolve_next_agent` / `next_turn_agent`）は本要件を識別するための規準名である。設計段階で `HandoffGraph` への統合等により別名・別配置を採る場合は、対応関係を ADR に記録したうえで変更してよい（本書は意味論＝適用条件・挙動・制約の SoT）。

## 1. 概要

openai-agents SDK のマルチターン継続は `Runner.run(result.last_agent, ...)` の last_agent 継続が標準パターンだが、ハンドオフで専門エージェントへ遷移した後は次ターンも専門エージェントから始まり、会話を設計上の窓口（トリアージ等）へ戻す判断が呼び出しコードのターン毎の分岐に散らばる。本機能は「ハンドオフ遷移を経てエージェント X が回答を終えた場合、次ターンは Y から開始する」という上書きルール（到達元条件・到達時ハンドオフ禁止の opt-in 付き）を宣言レベルで固定し、run 完了結果から次ターン開始エージェントを解決する副作用のない関数と、ハンドオフで X に到達したターンで X の全 handoff を無効化し X 自身に回答を完了させる到達時ハンドオフ禁止（opt-in）、および解決・registry 解決・last_agent フォールバックを 1 回の呼び出しに畳む組み立てヘルパを提供する。lib は実行ループを持たず、宣言 + build-time 検証 + 解決に徹する（build-don't-run。次ターンの `Runner.run` 呼び出しは利用者コードが行う）。

## 利用イメージ（抽象コード・非規範）

本節は利用イメージを掴むための抽象コード（擬似コード）であり、規範ではない（規範は §2 の受け入れ基準）。`NextTurnPolicy` / `resolve_next_agent` / `next_turn_agent` は命名注記の規準名。`NextTurnRule(...)`・`force_next=...`・`no_handoff_on_arrival=True`・`from_=...` は「上書きルール（次ターン指定・到達時ハンドオフ禁止・到達元条件）の宣言形」の仮表記であって規準名ではない。ポリシー宣言を実行構成へ結線する形（到達時ハンドオフ禁止が働くための build）・コンストラクタ細部・配置は設計段階（ADR）で確定する。

```python
# 前提: triage -> billing / tech、server -> billing への handoff を持つ構成が registry に
# 登録済みで、policy を結線した構成で実行している（結線形は設計段階で確定）。

# 宣言（FR-1）: 回答者 X -> 単一ルールまたはルールの列。
policy = NextTurnPolicy(
    rules={
        # billing はルールの列: 到達元で分岐する。
        "billing": [
            # triage からの到達: ハンドオフ禁止 + 次ターンは triage を強制指定。
            NextTurnRule(force_next="triage", no_handoff_on_arrival=True, from_="triage"),
            # それ以外（server 等）からの到達に一致する包括ルール: 禁止のみ
            # （次ターン指定なし = FR-2 は「上書きなし」で次ターンは last_agent 継続）。
            NextTurnRule(no_handoff_on_arrival=True),
        ],
        "tech": "triage",  # 次ターン指定のみの単一ルールは名前のみの略記
    }
)

# ターン 1: triage 起点で実行。triage からのハンドオフで billing に到達した時点で、
# 一致ルール（`from_="triage"`）の到達時ハンドオフ禁止により billing の全 handoff が
# 当該ターンに限り無効化され（FR-3・元実体と registry は不変）、billing 自身が回答を終える。
result = await Runner.run(registry.get("triage"), user_input, session=session)

# --- (1) 主経路: FR-4 ヘルパで次ターン開始 Agent を 1 回の呼び出しで組み立てる ---
next_agent = next_turn_agent(policy, result, registry)
# 上書き発動時（ハンドオフ経由 + 回答者一致・FR-2）: triage を registry から解決した Agent。
# 非発動時: result.last_agent（last_agent 継続パターンへのフォールバック）。
# 次ターンは開始エージェントの指定のみで、triage の handoff 構成に制限は掛からない。
if next_agent is not None:
    result = await Runner.run(next_agent, next_input, session=session)
else:
    ...  # フォールバックの last_agent も取得不能（開始エージェント決定不能。FR-4 の
         # 「last_agent 取得不能時は None + logger.debug」の基準）。
         # resolve_next_agent の None（上書きなし）とは意味が異なる。扱いは利用者の判断。

# --- (2) 単体 API の合成形: FR-4 を使わず FR-2 を利用者コードで分岐する ---
name = resolve_next_agent(policy, result)  # str = 上書き先の名前 / None = 上書きなし（正常系）
if name is None:
    agent = result.last_agent  # 従来どおりの last_agent 継続
else:
    agent = registry.get(name)
result = await Runner.run(agent, next_input, session=session)
```

### FR-1: 次ターン開始エージェントの宣言（`NextTurnPolicy`）

- ユーザーストーリー: ライブラリ利用者として、ハンドオフ後の会話の戻し先（回答者 X -> 次ターン開始 Y）をグラフ宣言と同じ宣言レベルであらかじめ固定したい。なぜなら、ターン毎の分岐を呼び出しコードへ散らばせず、会話の設計（誰が窓口か）を宣言として一元管理できるから。
- 受け入れ基準:
  - [ ] WHEN 利用者が上書きルールの集合（回答者名 -> 単一ルールまたはルールの列。各ルールは次ターン指定（Y）・到達時ハンドオフ禁止の opt-in・到達元条件の opt-in を持つ。次ターン指定のみの単一ルールは名前（str）のみの略記を許容）を `NextTurnPolicy` として構築する THEN 構築後に変更できない（frozen な）宣言オブジェクトが得られる
  - [ ] IF ルールのキー・次ターン指定・到達元条件のいずれかのエージェント名が str でない、または空文字である THEN 構築時（build-time）に `ValueError` で fail-fast する
  - [ ] IF ルールが次ターン指定と到達時ハンドオフ禁止のいずれも持たない（到達元条件のみ、またはすべて未指定）THEN 構築時に `ValueError` で fail-fast する（効果のない宣言の拒否）
  - [ ] IF 同一の回答者 X のルール列に、同じ到達元条件を持つルールが複数ある、到達元条件なしの包括ルールが 2 件以上ある、または列が空（ルール 0 件の空列）である THEN 構築時に `ValueError` で fail-fast する（発動ルールの選定が一意に決まらない宣言・効果のない宣言の拒否）
  - [ ] IF 上書きルールの集合（rules）が空（エントリ 0 件）である THEN 構築は成功する（no-op 宣言の許容。解決は常に「上書きなし」。エントリの値が空列である場合は前項により拒否される）
  - [ ] IF ルールの次ターン指定がキーと同名（X == Y）である THEN 構築は成功する（「X が回答したら次も X から」= 継続の明示固定として有効な宣言）
  - [ ] IF 同一の回答者名 X を持つエントリを複数与えようとする THEN 宣言は回答者名をキーとする Mapping で受けるため構築入力として表現できず、X のエントリは常に 1 件である（構造的排除。X に複数のルールを持たせる場合は値をルールの列として 1 エントリで宣言する。Python の dict リテラルで同一キーを重複記述した場合は言語仕様により後勝ちで正規化され、lib へは 1 件のみ渡る）。構築時に `dict(...)` で正規化し、反復と添字アクセスで異なる内容を返す独自 Mapping による迂回を防ぐ（既存 `FailsafePolicy.handlers` と同一方針）
  - [ ] WHEN 名前解決可能なコンテキスト（`HandoffGraph` / `AgentRegistry` の登録名集合）と併せた整合検証を行う THEN ルール中に存在しないエージェント名（キー・次ターン指定・到達元条件のいずれか）が含まれる場合は `ValueError` で fail-fast する
  - [ ] IF 整合検証を行わずに宣言単体で使う THEN 名前の実在は検証されないが、解決は失敗しない（宣言単体は名前空間を知らない。キー X が実回答者名と一致しなければ FR-2 の「最終回答者名がどのキーとも一致しない場合は上書きなし」の基準が適用される。次ターン指定 Y の実在性は本機能では検証せず、利用者側の registry 解決時に検出される。到達元条件の実在性も宣言単体では検証されず、一致する到達が存在しなければ発動しないことへ安全に倒れる）

### FR-2: run 完了結果からの次ターン開始エージェント解決（`resolve_next_agent`）

- ユーザーストーリー: ライブラリ利用者として、run の完了結果と宣言から次ターンの開始エージェントを 1 つの関数で解決したい。なぜなら、last_agent 継続パターンの置き換えが呼び出し側 1 行で済み、「ハンドオフ経由で X が回答したか」の判定を自前実装せずに済むから。
- 受け入れ基準:
  - [ ] WHEN ターン内にハンドオフ遷移が 1 件以上観測され、かつ最終回答者名が X（`RunResult.last_agent` の名前が X）で、X のエントリから発動ルールが選ばれ、そのルールが次ターン指定 Y を持つ THEN `resolve_next_agent(policy, result)` は Y を返す
  - [ ] WHEN X のエントリ（単一ルールまたはルールの列）から発動ルールを選ぶ THEN 「そのターンにおける X への最後のハンドオフ到達の遷移元と一致する到達元条件を持つルール」を第一候補、無ければ「到達元条件なしの包括ルール」を第二候補として選び、どちらも無ければ発動ルールなしとして「上書きなし」を返す
  - [ ] IF 発動ルールが次ターン指定を持たない（到達時ハンドオフ禁止のみのルール）THEN 「上書きなし」を返す（FR-3 の禁止はターン内で既に働いており、次ターンは従来どおり last_agent 継続等を利用者が選ぶ）
  - [ ] IF ターン内にハンドオフ遷移が 1 件も観測されない（開始エージェントがそのまま回答した）THEN 宣言に回答者のルールがあっても「上書きなし」を返す（利用者は従来どおり last_agent 継続等を選ぶ）
  - [ ] IF 最終回答者名が宣言のどのルールのキーとも一致しない THEN 「上書きなし」を返す
  - [ ] IF 判定材料（`last_agent` / ハンドオフ遷移）が結果から取得できない（属性消失、および属性アクセス時の例外送出を含む）THEN 例外を送出せず「上書きなし」を返し、`logger.debug` に理由を記録する（防御的解決。既存 Failsafe の防御方針と同型）
  - [ ] WHEN 解決を実行する THEN 入力（宣言・結果オブジェクト）を変更せず、LLM 呼び出し・ネットワーク I/O・ディスク I/O を行わない（副作用のない決定）
  - [ ] WHEN 同一の入力で複数回解決する THEN 常に同一の結果を返す（決定的）
  - [ ] IF `run_streamed` の完了結果が判定材料（`last_agent` / handoff アイテム）の同等属性を持つことを設計段階の実測で確認できない THEN streaming 完了結果への適用を非対応として docs に明記する（未検証のまま対応と主張しない）

### FR-3: 到達時ハンドオフ禁止（opt-in）

- ユーザーストーリー: ライブラリ利用者として、上書きルールの回答者 X にハンドオフで到達したターンでは、X の全 handoff を無効化して X 自身に回答を完了させたい。なぜなら、X からのさらなるハンドオフ（たらい回し）を断ち、X が回答してターンが終わるという会話設計を決定的にしたいから。
- 受け入れ基準:
  - [ ] WHEN ターン内のハンドオフで X に到達する THEN その到達ごとに「到達の遷移元と一致する到達元条件を持つルール」を第一候補、無ければ「到達元条件なしの包括ルール」を発動候補として選び（FR-2 と同一の選定規則）、選ばれたルールが到達時ハンドオフ禁止を宣言していれば、その到達以降の X は全 handoff が無効化された状態で動作し、当該ターンは X 自身が回答を終える（handoff 以外のツール・応答生成は不変）
  - [ ] IF 選ばれたルールが到達時ハンドオフ禁止を宣言していない、またはどのルールも選ばれない THEN その到達では禁止は発動せず、X の handoff 構成は通常どおり働く
  - [ ] IF X をターン開始エージェントとして直接使う（ハンドオフによる到達でない）THEN 禁止は発動せず、X の handoff 構成は通常どおり働く（非発動は開始時点の X に限る。直接開始した X から他エージェントへ handoff し、同一ターン内のハンドオフで X へ再到達した場合は、その到達以降について発動する）
  - [ ] IF どのルールにも到達時ハンドオフ禁止を宣言しない（既定）THEN X の handoff 構成は一切変更されない
  - [ ] IF X が handoff を元々持たない THEN 禁止は no-op として成功する（エラーにしない）
  - [ ] WHEN 禁止が働く THEN 元のエージェント実体・registry の登録内容は変更されない（無効化は run 単位の到達記録と build 時合成ゲートに閉じ — 実体の複製・書き換えなし — 、以降のターン・他の経路では元の構成が使われる）
  - [ ] WHEN ポリシー宣言の到達時ハンドオフ禁止が無効化を適用する THEN その無効化の意味論は全 handoff 一括・元実体不変・handoff 以外のツール / 応答生成は不変である
  - [ ] WHEN 到達時ハンドオフ禁止が働いた到達がある THEN X はその時点以降当該ターン中 handoff できず、その到達が X への最後のハンドオフ到達になる（FR-2 の発動ルール選定と FR-3 の到達ごとの選定は同一の規則を同一の最後の到達に適用することになり、判定はズレない）
  - [ ] IF FR-1 / FR-2 のみが先行リリースされ FR-3 が未提供である THEN FR-1 / FR-2 の宣言・解決は禁止機能なしで完結して動作する（段階的リリース可能な分離）
  - [ ] WHEN 到達時ハンドオフ禁止の SDK 前提（run ごとの `RunContextWrapper` 新規生成・記録と参照の間でのインスタンス同一性・handoff 有効性のステップ毎評価・無効 handoff のモデル非提示）に依存する THEN その前提を SDK バージョン耐性トリップワイヤの監視対象に含める（NFR-5）

### FR-4: 次ターン開始 Agent の組み立てヘルパ（`next_turn_agent`）

- ユーザーストーリー: ライブラリ利用者として、次ターンの開始 Agent 実体を 1 回の呼び出しで取得したい。なぜなら、解決結果（名前 or 上書きなし）の分岐・registry 解決・last_agent フォールバックを毎ターン自前の if/else で書くのは冗長で、分岐の書き誤りの温床になるから。
- 受け入れ基準:
  - [ ] WHEN 上書きルールが発動する状況（FR-2 の解決が Y を返す）で `next_turn_agent(policy, result, registry)` を呼ぶ THEN Y を registry から解決した Agent 実体を返す
  - [ ] IF 上書きルールが発動しない（FR-2 の解決が「上書きなし」）THEN `result.last_agent` を次ターン開始 Agent として返す（last_agent 継続パターンへのフォールバック。実現形が要する場合は同名の元実体へ正規化して返す — 技術的制約 3 の「last_agent 継続の復元」参照）
  - [ ] WHEN 到達時ハンドオフ禁止が発動したターンの結果からフォールバックする THEN 返る Agent で開始する次ターンは元の handoff 構成で動作する（禁止は当該ターンを越えて持続しない。禁止のみルールの発動ターンが該当する典型）
  - [ ] IF フォールバック時に `result` から `last_agent` が取得できない（属性消失、および属性アクセス時の例外送出を含む。SDK の `last_agent` は release 後アクセスで例外を送出しうる）THEN 例外を送出せず None を返し、`logger.debug` に理由を記録する（NFR-5 の防御方針と同一。呼び出し側は None を「開始エージェント決定不能」として扱える）
  - [ ] IF 発動した上書き先 Y が registry に未登録である THEN registry の名前解決エラー（`KeyError`）を握り潰さずそのまま伝播する（FR-1 の「値 Y の実在性は利用者側の registry 解決時に検出される」の検出点が本ヘルパになる）
  - [ ] WHEN 本ヘルパを呼ぶ THEN 結果オブジェクトと registry の登録内容を変更せず（`registry.get` の通常の遅延構築・キャッシュは変更に当たらない）、LLM 呼び出し・ネットワーク I/O・ディスク I/O を行わない
  - [ ] IF 本ヘルパを使わない THEN FR-1 / FR-2 / FR-3 の単体 API のみで従来どおり利用できる（本ヘルパは FR-2 + registry 解決 + last_agent フォールバックの合成であり、既存 FR の意味論を変更しない。到達時ハンドオフ禁止（FR-3）はターン内で完結するため本ヘルパは無効化処理を含まない）

### FR-5: 1 ターン限りの handoff 無効化プリミティブ（提供しない）

提供しない。到達時のハンドオフ禁止は FR-3 が担う。ターン開始エージェントに対する 1 ターン限りの無効化を行いたい場合は、SDK 標準の `Agent.clone(handoffs=[])` を利用者コードで直接使う（lib は API を提供せず、変形インスタンスの管理は利用者責任。docs に注記する）。不採用理由: 複製なし・利用者 context 非汚染・並行 run 安全を同時に満たす実現形が存在しないため（設計段階のユーザー判断で clone 方式を全廃・初版スコープ一覧参照）。

## 3. 非機能要件

### NFR-1: 保守性（SDK 隔離）
- 要件: 新規の宣言型・判定ロジックは `agents` 非依存層に置く。`from agents` / `import agents` は `src/oai_agentspec/_adapters/` 配下のみで許容し、結果オブジェクトからの観測値抽出・到達時ハンドオフ禁止の合成（on_handoff / is_enabled ゲート）の SDK 結合は `_adapters` に閉じる。
- 計測基準: `grep -rnE "(from agents|import agents)" src/oai_agentspec/ | grep -v _adapters` の結果が空。

### NFR-2: 保守性（build-don't-run）
- 要件: 公開 API に実行ループ・`Runner` 参照・次ターンの自動実行を追加しない。解決は入力（宣言 + 結果）から出力を計算する関数に徹する。
- 計測基準: 新規公開 API の実装に `Runner` 参照・再試行ループが存在せず、判定ロジックが `agents` 非依存の単体テスト（L1）だけで検証できる。

### NFR-3: 互換性（公開 API 契約・既定挙動不変）
- 要件: 既存公開シンボルの振る舞い・シグネチャは不変。本機能を宣言しない既存コードの挙動は一切変わらない（純粋追加）。新規公開シンボルのコア `__all__` への追加は本要件書の承認をもって合意とし、既存メンバの削除・改名は行わない。
- 計測基準: 既存テストスイート（`uv run pytest`）全緑を維持し、公開 API スモーク（`__all__` 全件 import）が通過する。実装前後で既存 `__all__` メンバが 1 件も削除・改名されていない。

### NFR-4: 性能
- 要件: 解決は run 完了結果の 1 回の走査（ターン内アイテム数に線形）で完了し、LLM 呼び出し・ネットワーク I/O・ディスク I/O を伴わない。
- 計測基準: 解決関数の単体テストが外部 I/O のモックなしで完結する（純計算であることの構造的証明）。

### NFR-5: 保守性（SDK 結合点の防御）
- 要件: 判定材料（`last_agent` / handoff アイテム）の属性読み取りは防御的に行い（`getattr` による欠落許容に加え、読み出し自体が送出する例外の捕捉を含む）、属性欠落および属性アクセス時例外を安全側（FR-2 は「上書きなし」・FR-4 のフォールバックは None）へ倒す。防御方針は既存 Failsafe の `last_agent` 解決（読み取り先ごとの防御・`logger.debug` 記録）と同一とする。本結合点、および到達時ハンドオフ禁止の SDK 前提（`RunContextWrapper` の run ごと新規生成と記録・参照間の同一性・handoff 有効性のステップ毎評価・無効 handoff のモデル非提示）を SDK バージョン耐性トリップワイヤ（SDK 結合点の前提属性をテストで pin し、SDK 更新時の静かな退行を CI で検知する既存方針。`docs/architecture.md` のテスト層節参照）の監視対象に含める。
- 計測基準: 判定材料の属性を欠いた結果オブジェクト、および属性アクセス時に例外を送出する結果オブジェクトのそれぞれを与えるテストで、例外が送出されず安全側の値（FR-2 相当は「上書きなし」・FR-4 のフォールバック相当は None）が返る。

### NFR-6: 保守性（テストカバレッジ）
- 要件: 追加コードを含め既存の `fail_under = 80` を維持する。
- 計測基準: `uv run pytest` がカバレッジゲート込みで緑。

## 4. 制約事項

- **技術的制約 1（build-don't-run）**: 次ターンの実行（`Runner.run` 呼び出し）は利用者コードが行う。lib が提供するのは宣言・解決・到達時ハンドオフ禁止の build 時結線までであり、公開の実行 API・自動継続ループは追加しない。
- **技術的制約 2（SDK 結合点）**: 判定材料は run 完了結果の `last_agent` / `new_items`（handoff アイテム。到達元条件の判定にはその遷移元・遷移先を用いる）に依存する SDK 結合点である。アイテム判定は既存 `observe_run_result`（`_adapters/routing.py`）と同型の防御的読み取り（属性の有無で判定・`type` リテラル非依存）とし、加えて属性の読み出し自体が送出する例外（SDK の `last_agent` property は release 後アクセスで例外を送出しうる）も捕捉して安全側へ倒す（NFR-5 参照）。
- **技術的制約 3（到達時ハンドオフ禁止の実現形）**: 到達時ハンドオフ禁止は、(1) build 時に確定する判定表（どの（遷移元, X）到達で X の handoff を無効にするか）と、(2) SDK の公式拡張点（handoff の `on_handoff` / `is_enabled`）への build 時合成で実現する。エージェント実体の複製・差し替え・事後書き換えは行わない。ターン実行中に lib が行ってよいのは「到達事実の記録（run 単位に分離された lib 内部ストアへの追記。利用者 context への書き込みはしない）」と「判定表 + 記録の参照による有効/無効の返却」のみであり、判定表・宣言の実行中変更、SDK 内部 dispatch への割り込みは行わない。記録は run（`RunContextWrapper` インスタンス）単位に分離し、run 終了後は弱参照により解放される。**last_agent 継続の復元**: 禁止が発動したターンの `result.last_agent` は元のエージェント実体であり、次ターン（新しい run）には到達記録が存在しないため、FR-4 のフォールバック経由・利用者による生の継続のいずれでも次ターンは元の handoff 構成で動作し、禁止が当該ターンを越えて持続しない。前提外の利用（`RunContextWrapper` インスタンスを利用者が自作し複数 run で再利用する場合・HITL 再開の resume）は非対応として docs に明記する。
- **技術的制約 4（到達時ハンドオフ禁止の保証範囲）**: 保証するのは「到達時ハンドオフ禁止を宣言した X にハンドオフで到達した以降、当該ターンで X からの handoff 遷移が実行されない」ことまでである。LLM の応答内容（他エージェントへ回したがる文面等）は制御しない。session 履歴も改変しない。次ターンの開始エージェント（Y）の handoff 構成には制限を掛けないため、次ターンで再び X へハンドオフされる可能性は仕様上許容される（その場合も X 到達時に禁止が再度働き、宣言どおり X が回答を完了する）。
- **技術的制約 5（Realtime 非対応）**: `RealtimeRunner` / `RealtimeSession` はライフサイクルが異なるためスコープ外。
- **ビジネス制約 1（段階的リリース）**: FR-3（到達時ハンドオフ禁止）は FR-1 / FR-2 と独立の要件・受け入れ基準を持ち、FR-1 / FR-2（および FR-4）のみの先行リリースを可能にする。FR-4 は FR-1 / FR-2 のみに依存する。
- **ビジネス制約 2（公開契約の合意）**: 新規公開シンボルの追加（コア `__all__` の変更）は本要件書の承認を合意とする。

## 6. 用語定義

| 用語 | 定義 |
|------|------|
| ターン | 1 回の `Runner.run` 呼び出し（開始エージェントへの入力から最終出力まで） |
| 回答者（X） | そのターンで最終応答を生成したエージェント。SDK `RunResult.last_agent` に対応する |
| ハンドオフ経由の回答 | ターン内に 1 件以上のハンドオフ遷移が観測され、かつ最終回答者が X であること。上書き適用の AND 条件（開始が X で他エージェントを経由して X に戻った循環ケースも含む） |
| 上書きルール | 回答者 X に紐づく宣言単位。次ターン指定（Y）・到達時ハンドオフ禁止（opt-in）・到達元条件（opt-in）を持ち、次ターン指定と禁止の少なくとも一方を含む。X のエントリは単一ルールまたはルールの列 |
| NextTurnPolicy | 上書きルールの集合を保持する frozen な宣言型（本書の規準名） |
| resolve_next_agent | run 完了結果と宣言から「次ターン開始エージェント名（str）または上書きなし（None）」を解決する副作用のない関数（本書の規準名） |
| next_turn_agent | 宣言・run 完了結果・`AgentRegistry` から次ターンの開始 Agent 実体を 1 回の呼び出しで組み立てる便宜ヘルパ（本書の規準名）。上書き発動時は Y の解決済み Agent を、非発動時は `result.last_agent` を返す。フォールバックの last_agent も取得不能な場合は None（開始エージェント決定不能。`resolve_next_agent` の None＝「上書きなし」とは意味が異なる） |
| 到達時ハンドオフ禁止 | 上書きルールの回答者 X にハンドオフで到達したターンにおいて、X の全 handoff を当該ターンに限り無効化し、X 自身に回答を完了させること（元実体・registry は不変。X をターン開始エージェントとして直接使う場合は発動しないが、直接開始した X に同一ターン内のハンドオフで再到達した場合はその到達以降について発動する。無効化の意味論は全 handoff 一括・元実体不変・handoff 以外のツール / 応答生成は不変。発動ルール（到達ごとの選定規則で選ばれたルール）が禁止を宣言している到達のみが対象） |
| 到達元条件（from） | 上書きルールに opt-in で併記する、発動を特定の遷移元からのハンドオフ到達に限定する条件（仮表記 `from_`）。ルール列では「一致する from を持つルール → from なし包括ルール → なし」の順で発動ルールを選ぶ（FR-2 は最後の到達・FR-3 は各到達に適用）。未指定は到達元不問（既定挙動不変）。1 ルールの到達元条件は単一名 |
| last_agent 継続パターン | SDK 標準のマルチターン継続 `Runner.run(result.last_agent, result.to_input_list() + 新入力)`。本機能はこのパターンの開始エージェント選択を宣言で上書きする |
| build-don't-run | lib は宣言・build-time 検証・薄い結線に徹し、実行は SDK `Runner.run` に寄せる本リポジトリの設計原則 |
